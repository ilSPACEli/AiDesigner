# Правила потоку (Канбан, ЛР №8–9)

Дошка: GitHub Projects → подання **«Канбан»** (Board, групування за `Status`). Стартовий стан продукту — `v2.0.0`.

**Стани задачі:**
`To Do` → `In Progress` → `Review` → `Done`.

| Стан | Що означає |
|---|---|
| `To Do` | задача сформульована (картка з описом і критерієм готовності), пріоритет визначено, можна брати |
| `In Progress` | виконавець працює; є гілка й draft PR |
| `Review` | PR готовий до рев'ю, CI зелений; чекає перевіряльника |
| `Done` | PR злито в `dev`, перевірку виконано й прийнято, картку закрито |

**Початок і завершення роботи:**
- Початок — картка перейшла `To Do → In Progress` (виконавець призначений, гілка створена).
- Завершення — картка перейшла `Review → Done` (злиття + підтвердження перевіряльника).
- Межі вимірювання для показників потоку: **тривалість виконання** = від `In Progress` до `Done`.

**Умови переходу між станами:**
- `To Do → In Progress`: є виконавець; WIP-ліміт не перевищено; беремо картку з найвищим пріоритетом.
- `In Progress → Review`: код і тести в PR, CI зелений, у PR — посилання на картку й опис перевірки.
- `Review → In Progress`: перевіряльник залишив зауваження, що потребують змін.
- `Review → Done`: Approve перевіряльника, злиття в `dev`, у картці — посилання на PR і результат перевірки.
- Кожен перехід записується в спільну таблицю подій потоку в момент переходу (фактичний час; доказ — Issue для старту, PR або коментар у картці для `Review` і `Done`). Наприкінці ЛР №8 таблицю експортовано в [flow-events.csv](flow-events.csv); підсумок — [flow-summary.md](flow-summary.md).

**Ліміт незавершеної роботи та стани, які він охоплює:**
- **WIP = 3** — спільний для `In Progress` + `Review` (команда з 4 осіб: щонайменше один вільний для рев'ю).
- Перед тим як узяти нову картку, учасник рахує картки в цих двох станах. Ліміт вичерпано → спершу допомогти завершити розпочате (рев'ю, перевірка, розблокування).
- Заблокована задача **рахується** в ліміт.

**Дії в разі блокування:**
- Додати до картки мітку `blocked` і коментар: що заважає, від кого / чого залежить, дата.
- Повідомити в чаті команди; Фріз (координатор) протягом дня або знімає блокування, або повертає картку в `To Do`.
- Блокування довше 2 днів — обговорити на найближчій зустрічі (розділити задачу або змінити пріоритет).

**Хто та як перевіряє результат:**
- Перевіряльник — **не автор**; призначається в картці (поле «Перевіряльник»).
- Перевіряє: код і тести в PR, зелений CI, за потреби — сценарій через клієнт (запущений сервер).
- Для дефекту: тест **падає** на дефектному коміті й **проходить** після виправлення з тим самим очікуванням.

## Ризики продукту й перевірки

| Ризик | Вимога / правило | Перевірка | Рівень |
|---|---|---|---|
| Робота з великого фото не зберігається в галерею (#53) | FR-14, NFR-06 (фото до 10 МБ), NFR-07 | регресійний тест збереження великого результату; ручна — через UI | інтеграційний (`DesignService` + клієнт + API) |
| Помилковий запис: робота без аналізу або аналіз без роботи | FR-21 (одна транзакція) | `ResultAnalysisTransactionTests` (AC-32, AC-33) | інтеграційний (SQLite) |
| Невірний добір предметів | R1–R6 | модульні тести правил (`R1_*`…`R6_*`, `AC06_*`) | модульний |
| ШІ не відповідає / зламана відповідь | FR-18, R8 (AC-28, AC-30) | тести з фейковими провайдерами | модульний |
| Галерея переповнюється / зловживання | R7, NFR-07 | `AC23_*`, `AC24_*` | інтеграційний (API) |
